## 多格房间

此前生成器限制主路为单格，所以部分“只显示 1×1”来自真实生成限制；渲染器又在同一房间每格之间保留边距并逐格描边，导致已存在的大房也像多个独立格。
当前允许主路实际采用可容纳的 2～4 格模板，并仍预留后续主路和首领位置；当前内容池的主路保证至少一个多格房，保持主路唯一、早期支路和割边门禁。
RoomMapGeometry 只对同一逻辑房间的外边界留边并描线，内部格无缝连接，保留 L/T/十字缺角；不同房间通过门连通仍保留各自边界，标签放在实际占用格内。
HUD 和大地图共用该纯几何实现，开发示意图也直接导出同一实现的矩形，不另写一个看起来不同的地图算法。

## 传送门

封印大厅完成后，其首领出口中央生成 2×3 的 `saodg:blood_portal`，使用引用原版纹理的透明方块，无物品/掉落/方块实体。
这是同实例内触碰触发器，不是原生跨维度传送门，不会把队伍送往下界。
封印大厅侧可进入，背后的首领侧仍有实体阻挡；触碰后才保存首领阶段/钥匙消费并把在线未淘汰、存活成员一起移至首领落点。
本局已确认死亡或主动退出者不重新入场，离线成员保持原重连/回程策略；原生濒死状态不由此重置。目标整合包中的濒死与传送仍须实测。
触发须为实际在线玩家对象、实际身体与方块重叠、属于本局已完成封印大厅出口、正确阶段和钥匙；其他队员资产冻结或状态未知时不开始。
发生部分传送/刷怪失败则转为中止并使用原回程记录；重复方块触碰不能重复耗钥匙/刷首领。主界面移除逐人准备按钮，正常流程进入紫色传送门；旧 bossready API 保留兼容。
普通支路无人时暂停其波次等待与超时，不把卸载当成确认死亡；首领开始后暂停支路刷怪/缺失检查，避免整队离开支路造成错误中止。仍在加载的越界受管怪会被拉回，不清房、不发奖励。

## 实际执行

完整命令 `gradlew.bat build runGameTestServer -PgameTestRunDirectory=run/gameTestServer-portal-2026-10-28 --offline --console=plain`。
最终 `logs/portal-map-complete-2026-10-28.log`：89 项 JUnit、38 项 required GameTest 全部通过，退出 0，2 分 34 秒。
地图增加六项纯几何检查：HUD/面板尺寸下 2×2 内部无缝，L/T/十字只有一个像素连通区域且不填缺角，两个不同房间不被误合并。
三难度各 10000 内容种子继续验证多格主路、固定起点、主路割边、早期支路、封印大厅远端和转折边界。
实局夹具第一局包含两个真实 PlayerList 成员；一人从封印大厅通过原生 Entity.move 进入实体传送门，另一个一直在别处，随后两者均在首领房。
证明首领钥匙只消耗一次，复制同 UUID 的未登录对象不能触发，重复接触不能多刷首领；随后第二成员退出，原首领阈值/封印/完整冲锋/动态墙/最终确认死亡继续通过。
这是一台独立 Forge 专服中的两个真实服务端人物和嵌入连接，不能称为两个真实客户端联机验收。
