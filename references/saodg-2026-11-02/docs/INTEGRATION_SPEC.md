# SAODG 与现有 SAO / KubeJS 集成契约

设计稿 v0.1，2026-10-27。本文是[完整方案](DUNGEON_DESIGN.md)的目标契约；当前已写入源码的查询、注册桥接和脚本材料见[集成实现说明](INTEGRATION_IMPLEMENTATION.md)。本轮暂停构建/运行验收，不能据此认定实际 SAO/KubeJS/FTB 兼容已通过。

## 1. 接入基线与核对方式

已检查本机服务端目录中的 `mod_1cab0b39_1cab0b39-1.2.0-r234.jar` 公共方法，以及现有静态脚本仓库的相关脚本；没有据此确认远程服务器正在运行同一套文件。正式适配以实际 SAO 核心、`sao-gameplay-fixes` 和其他战斗/职业补丁的哈希清单为准。

开发流程：记录客户端与服务器JAR哈希 → 检查实际字节码方法签名 → 查看相符源码 → 为公共接口写运行时探测 → 在目标整合包做GameTest/联机验收。旧源码里的等级公式、队伍上限和事件顺序不等于补丁加载后的行为。

独立基础模式只要求 Forge；服务器预设则明确要求 `sao-profile`、`sao-downed`、`sao-party`、`pack-wallet` 等能力可用。缺失或版本不匹配返回 `NOT_READY`/`UNSUPPORTED`，界面解释原因并拒绝开新局。

## 2. 已有能力与新增适配

| 能力 | 已有入口/现状 | SAODG 的使用方式 |
| --- | --- | --- |
| 攻略资料 | `cn.blockforge.generated.mod1cab0b39.PlayerData.level(Player)`、`resource(Player)`、`get(Player)` | 只在 `integration/sao` 调用；不自行复制等级公式 |
| 职业 | 现有源码 `Professions.role(ServerPlayer)` 与 `PlayerData` 职业字段 | 在真实JAR核对签名后适配；未知职业显示未知，不假设角色编号永远不变 |

| 社交队伍 | `com.sao.saomenu.party.SAOTeamManager.teamOf(server, player)` | 返回原生队伍或null；选定在线成员后固定本次UUID名单 |
| 客户端原生同步 | `SaoNetwork.sync(ServerPlayer)` | 仅在合法改变SAO状态的适配流程中调用；迷宫区地图使用自己的网络 |
| SAO经验 | `PlayerData.xp(ServerPlayer, int)` | 原生击杀经验保留；启用奖励的新局另按难度/评分固定通关奖励，统一经原生经验回执提交 |
| 珂尔余额 | 当前 KubeJS 2001.6.5-build.26 钱包为玩家文件 `KubeJSPersistentData.PlayerPersisted.sao_kol_balance`，现有钱包模块拥有 | 不由SAODG核心直接读写或发旧币；不能与 ForgeData 中同名字段混用 |
| 钱包公开函数 | `global.saoWalletBalance`、`global.saoWalletTransact`、`global.saoWalletSavePlayer` | 可作扩展基础，但当前不等于通用持久领奖事务 |
| FTB进度 | 现有任务线 ports 使用FTB `TeamData` | 由脚本适配事实与解锁条件，不让引擎依赖FTB队伍 |

`SAOTeamManager` 当前可见公共查询没有提供稳定的队长UUID；不能把计分板队伍显示名当权限。SAODG 大厅创建者拥有大厅操作权，各成员保留逐次确认权。

原生救援和职业同队增益仍查询当前SAO队伍；固定的本局名单不自动扩大这类权限。首发保持原生关系，局内换队给明确提示但不改原计分板队伍；跨实例效果始终额外校验实例归属，不能凭社交同队绕过。

## 3. 模块依赖与对外接口

构建只在兼容源集/包中以 `compileOnly` 和 Forge 对应反混淆方式引用目标SAO JAR；不把SAO类或JAR打进SAODG。KubeJS同样是可选编译/运行集成。选择具体Gradle写法后，验证开发环境命名与重混淆产物两条路径。

类加载隔离必须保证没有安装SAO/KubeJS时仍能启动专用服务器。只有依赖存在且版本探测成功后才装配对应适配器；基础领域对象和公共网络包不携带外部类。

### 3.1 拟新增端口

| 端口 | 输入/输出与约束 |
| --- | --- |
| `PartyProvider` | 玩家UUID → 已知/未知的队伍视图与成员UUID；无队伍可单人开本 |
| `PlayerProfileProvider` | 玩家UUID → 已知等级/职业/濒死状态；区分未知与false |
| `AdmissionPolicy` | 已冻结候选名单、迷宫区、难度 → 允许/拒绝及每人原因 |
| `RewardTransactionPort` | 持久操作ID与服务端固定奖励 → `APPLIED / ALREADY_APPLIED / RETRY / REJECTED / UNCONFIRMED` |
| `ConfirmedFactSink` | 带唯一ID的房间/通关事实 → 已确认/可重试 |
| `SaveBarrier` | 保存并确认指定操作回执已持久化；不能只依赖日志没有报错 |
| `OwnerResolver` | 玩家/实体/伤害上下文 → 已知玩家UUID或未知；禁止猜测最后一位附近玩家 |

基础模式提供自己的小队大厅、原版角色信息和原生物品奖励适配；服务器正式预设选用SAO与钱包适配，不因缺失脚本自动回退到可能改变经济的另一实现。

当前源码另提供自有迷宫区成长与数据包 admission 前置：等级只读取已确认的迷宫区 XP，通关次数只索引新结果中的显式最终资格凭证。
该检查针对每位成员，与 KubeJS/SAO/FTB 入场条件叠加；不替代原任务、原角色等级或正式预设的安全门槛。字段与升级兼容见[开发说明](DEVELOPMENT.md)。

### 3.2 拟新增查询与请求

`DungeonApi` 提供 `isManaged(entity)`、`findRun(playerId)`、`findMemberState(playerId)` 等只读查询。返回不可变快照，外部不能直接拿到运行实例Map或背包对象。

开局、交互和领奖经用例请求执行，重新验证服务端条件。`runId`、`roomId`、`operationId` 都是标识，不是客户端持有就能获得权限的凭证。

所有API有版本号与明确线程要求：权威查询/修改在所属服务器主线程；客户端只有服务端镜像。未知未来枚举值必须容忍，失败不得返回虚假的成功。

## 4. KubeJS 插件与脚本生命周期

拟提供服务端绑定 `saodg` 和事件组 `SaodgEvents`。这是新API，不是现有KubeJS自带功能。待实现后再公布最终方法签名、字段映射和Rhino可见类型。

推荐脚本文件：

```text
kubejs/server_scripts/
  sao_dungeon_admission.js       开放条件与入口NPC联动
  sao_dungeon_wallet.js          持久奖励事务与确认
  sao_dungeon_quests.js          FTB事实投递
  sao_dungeon_compat.js          旧脚本统一判断/健康报告
```

定义加载优先使用JSON/数据包；脚本用于服务器特有策略与连接现有服务。不要把每tick房间调度、怪物AI和实例数据放在JavaScript全局变量中。

### 4.1 事件语义

| 拟新增事件 | 何时发布 | 可否取消/重放 |
| --- | --- | --- |
| `beforeRunStart` | 固定候选名单后、分配地图前 | 可拒绝；事件结束后服务端再次校验 |
| `roomCompleted` | 房间完成持久事实已登记 | 不可取消；可按factId重放 |
| `runCompleted` | 结果与个人奖励方案已持久化 | 不可取消；不代表物品已经到账 |
| `runAborted` | 系统中止事实已登记 | 不可取消；区分玩家失败 |
| `rewardClaimRequested` | 进入受控领奖用例 | 仅用于已注册适配器；不能让任意监听者各自发奖 |
| `rewardCommitted` | 玩家回执确认后 | 不可取消；可以因恢复而重放，监听者须去重 |

关键经济动作由单一 `RewardTransactionPort` 处理；普通事件监听只观察或投递幂等事实。仅发一个事件然后假设钱包成功，不满足事务要求。

### 4.2 `/reload` 与关闭

适配器在脚本加载时登记，在调用时解析当前有效服务；不用开局时捕获的旧JavaScript闭包处理几小时后的领奖。脚本重载开始时停止新开本/新领奖，重新登记和健康检查后恢复。

运行中的Java实例继续持有自己的定义快照；脚本不可用期间奖励停在待处理状态，不能换成本地金币。停服清除临时绑定和运行对象，持久日志保留。startup桥接或新Java注册必须重启。

## 5. 受管实体标识与实例权限

拟使用实体Forge持久数据下的 `saodg` compound：

```text
schema: 1
run_id: UUID
room_id: resource/local ID
encounter_id: UUID
role: required_enemy | optional_enemy | boss | summon | projectile
owner_player: optional UUID
parent_entity: optional UUID
reward_policy: managed_completion | native_kill_only | none
```

该标记用于路由与恢复，不能单独授予权限。权威运行注册表必须核对该UUID确实属于本局、实体类型匹配且未被回收。管理员命令生成带同样NBT的实体不能伪造领奖。

KubeJS的 `getPersistentData()` 与Java的Forge持久数据不能未经测试就假设完全相同。公开 `saodg.isManaged(entity)` 作为统一入口，必要时桥接有限的脚本可见标记，GameTest验证两侧一致。

宠物/召唤物默认不修改原生Owner字段，仅保存本次实例租约。退出解除租约，召回或安全归还既有宠物；不把玩家原有宠物当作副本杂兵清除。投射物继承主人/父实体实例；未知归属不授予击杀贡献，伤害策略按兼容白名单保守处理。

跨实例限制必须覆盖普通攻击、投射物、AOE、治疗、护盾、控制、拾取、机关、实体交互与位移。某些SAO技能直接设血/传送而不触发常规事件，需要逐项运行验收；必要补丁只在SAODG实例中生效。

## 7. 原生 SAO 奖励与死亡链

### 7.1 攻略经验

已读旧源码包含 `ExternalKillXp` 对外部生物发经验，以及 `SaoEvents`、`BossProgress`、`ImportedBoss` 等自己的奖励入口。取消物品掉落或原版经验球不等于阻止这些直接调用 `PlayerData.xp()` 的路径。

当前政策（2026-10-31）：允许原生 SAO 击杀 XP；启用奖励且已绑定原生经验接口的新局，另为有效参与成员提供固定通关经验。试炼/标准/精英分别为 90–180 / 180–360 / 360–720，按 0–300 分线性增加，不按人数平分、不跟随等级膨胀、不与付费箱档位挂钩。受管实体仍跳过 KubeJS 额外 XP 与珂尔；SAODG 副本经验仍单独保存。

通关结果先保存资格、经验所有者与策略版本，再生成每局每人唯一的原生 XP 请求；沿用现有意图、人物回执、保存回读与资产租约。历史结果无新字段时不追补，失败/中止/挂机不产生通关经验。SAO 仍独占等级曲线和上限；接口版本不匹配时等待，不写原生 XP 字段或改发原版经验。击杀请求仍要求原死亡链接，通关请求必须匹配持久化的成功结果，不用虚构死亡授权。

当前源码在已匹配的 `ExternalKillXp.onDeath` 实际调用 `PlayerData.xp` 处捕获原生资格、接收者和数额；受管怪不立即发放，也不再次派发死亡事件。
真实死亡及其链接持久确认后才把原请求交给原生经验函数，并以人物文件中的回执确认；离线时等待实际在线玩家，不构造替身，不由迷宫区复制 SAO 等级曲线。
原生 r234 与本地 `sao-gameplay-fixes` 曲线 v2 使用不同所有者标识，旧请求不会在版本变化后静默换公式。新源码与实际钩子、曲线、保存和重启行为仍未运行验收，正式预设继续阻断。

旧击杀目标与这条 XP 政策分别配置。新局默认 `allowLegacyKillObjectives=false`：受管怪不计入原版击杀记分/实体类型统计/对应击杀进度、旧 FTB KillTask 与兼容任务历史。
设为 true 则沿用这些旧入口的原行为；取值在开局保存，不因重载改写已有局，旧运行记录缺少该字段时保留原行为，不回滚已存在的统计/任务进度。
这项策略不关闭原生 SAO XP、SAO 个人 kills 字段或普通世界成长；自定义迷宫区 Boss 仍不能调用原生楼层胜利接口。

首发自定义Boss不继承原生主线Boss类型，不调用 `GuideWorld.onGuardKilled`、`BossProgress.record` 或伪造原生楼层胜利。复用原生/第三方Boss需要先验证其死亡方法本身是否发物品、改变主线或脱离实例。

0.41.34 新增原生 `MoonlightCrystalDrops.onDeath` 的限定适配：r234 此方法直接插入月光结晶实体，不经过 `LivingDropsEvent`，可能令临时场地清理进入未知物品隔离。仅对运行时登记且 UUID、实体类型和实际身体匹配的副本敌人跳过此额外物品回调；不取消整个死亡事件，不改原生 XP、普通世界或仅带伪造 NBT 的实体。沿用完整类散列匹配，管理员诊断 `moonlight-drops` 区分二进制匹配与回调实际观察。新策略不删除已经存在的结晶，也不放宽未知资产清理规则；既有隔离仍须先保全并处理物品。

### 7.2 死亡事实

玩家生命到零的事件可能被复活结晶或濒死机制取消；SAO源码在LOWEST优先级处理部分逻辑，因此SAODG不能假设在同优先级就能先后保证最终结果。

正确流程：收集候选死亡 → 让事件链结束 → 主线程后续tick确认实例成员状态、实际存活、濒死与重生关系 → 产生唯一死亡事实。复活结晶成功、被取消死亡、仍在濒死都不记阵亡；最终死后立即重生仍须从死亡/Clone链确认，不能只查询“当前UUID对应玩家还活着”。

对怪物同样确认真实死亡；传送、卸载、discard、阶段分身消失、插件清怪和管理员abort不算合法击杀。必要实体异常缺失时尝试定位/诊断，恢复规则有界，不无条件重刷产生刷取XP漏洞。

同一实体的取消/再次死亡按确切事件身份区分；互相冲突的非取消死亡来源或原生经验数额不猜测归属，转为系统中止。
原生经验请求先保存为等待死亡状态，与确认死亡在世界日志中建立链接，再保存为独立 READY 义务；链接未确认时不能清理其来源，READY 确认后可独立于地图继续处理。

`inherit`死亡策略在入场前检查现有世界及其他模组是否保留玩家资产。会遗留装备到临时实例的配置，必须先实现并通过保管/归还验收，否则正式预设拒绝开本；清理程序不能删除未知来源物品或靠全服改gamerule规避此问题。

## 8. 奖励事务：保证范围与单一提交者

### 8.1 不变量

- 同一玩家同一局的基础奖励最多提交一次；个人宝箱最多选择并领取一次。
- 同一操作的物品、珂尔扣/增款、攻略经验及玩家领取回执位于同一个玩家文件的提交边界。
- 世界账本可以暂时落后于玩家回执，恢复时以已确认的玩家回执对账；不得因此重新加物品。
- 不把跨多个文件的写入声称为原生原子事务；依赖持久意图日志、保存屏障和幂等接收方。
- 不确定是否保存成功时进入待确认状态，不通过盲目回滚/重发解决。

现有 `saoWalletTransact` 支持资金、物品、空间和某类任务回执，但没有SAODG通用operation契约。需要扩展钱包适配或增加同等强度的专用事务入口，不能复用任务线claim字段冒充迷宫区回执。

### 8.2 操作标识与记录

每个操作在服务端首次创建时分配稳定UUID并持久保存。基础奖励和个人宝箱使用不同操作ID；同一个宝箱操作绑定 `runId + playerId + choiceId + payloadHash + rewardVersion`，重试不重新生成UUID。

玩家文件保存：`PlayerPersisted.saodg.reward_receipts[operationId]`，包含内容散列、选择、提交版本与状态。迷宫区成长存入 `PlayerPersisted.saodg.progress`，同次提交；既有钱包余额字段不迁移。

世界账本保存固定RewardOffer、资格证据、操作状态和所有者，按UUID索引。客户端仅提交 `runId + offerId + revision + requestId`，绝不接受客户端提供价格、掉落NBT或奖励数量。

### 8.3 提交流程

1. 校验结果和奖励方案已经持久化；玩家属于本局且有资格；对该玩家与操作加主线程事务锁。
2. 先查玩家回执。已确认同散列操作返回 `ALREADY_APPLIED`；同ID不同散列拒绝并报告冲突。
3. 检查选择状态、余额、额度、所有物品可注册、精确NBT与背包容量，构造最终资产快照；不要先扣费。确认前的返回/取消不产生副作用。
4. 将固定选择和操作意图写入持久日志，保存屏障成功后锁定本次宝箱选择。不能在世界记录尚未保存时修改玩家资产。
5. 在钱包唯一事务入口中应用物品、余额、攻略经验及同一操作回执。回执进入 `APPLIED_UNCONFIRMED`，不能再次添加同批物品。
6. 调用保存屏障确认玩家文件中该操作及payload散列已经落盘，再把操作标记为已确认。保存屏障应检测实际保存失败；仅调用可能内部吞异常的 `saveAll()` 并看到返回，不足以认定成功。
7. 世界账本确认完成，发布 `rewardCommitted`；outbox稍后投递FTB或公告事实。世界确认落盘失败时可重试，玩家回执阻止二次扣发。

玩家保存结果不确定时保留内存中已应用标记，只重试保存/确认，不重做物品增量；禁止该玩家进行可能把未确认资产转出的新交易、丢弃或容器转移，直至确认或受控恢复。需验证整合包中其他模组不会绕过此暂停策略。

从磁盘读回带匹配payload的“已应用”回执，说明该玩家文件的同次资产快照已经保存，可将内存中的待确认状态推进为已确认；不能因为回执内仍写着 `APPLIED_UNCONFIRMED` 就再次加物品。离线/重启对账也使用相同规则。

保存屏障可以通过原生保存结果适配和可信玩家文件回读确认实现，具体方案在M3完成前确定。只有读回相符回执和提交信息才能回报已持久确认；不要仅核对一个全局内存布尔值。普通文件系统/硬件掉电损坏不在逻辑幂等可完全解决的范围内。

### 8.4 故障恢复表

| 中断位置 | 重启/重试处理 |
| --- | --- |
| 意图保存前 | 无资产修改，可重新选择 |
| 意图已保存、玩家尚未应用 | 读取原固定选择，校验后执行一次 |
| 玩家已应用、尚未确认写盘 | 在线只重试保存；重启后查玩家文件，有回执不重发，无回执按日志重试 |
| 玩家文件已确认、世界账本未更新 | 从回执修复世界状态，不再次扣费或发物品 |
| 世界已完成、客户端没收到回应 | 查询返回已领取，展示结果，不重做操作 |
| FTB投递失败 | 奖励保持已领取；outbox按factId重投，不再次支付 |

对未确认资产已被外部模组转出或回执冲突的异常，冻结对应操作并保留证据，不能提供无回执校验的“强制再发”命令。

### 8.5 入场费用和保底

v1免费入场。未来多人门票/珂尔入场要另做每人预留、全员确认、失败撤销和重启补偿协议，不能沿用单人宝箱事务假装全队资产原子。

保底、每日次数、首通奖励若会影响经济，和对应领奖回执同一提交；不在UI打开、奖励预览或未保存的完成事件中增加。

## 9. FTB 任务事实与旧统计旁路

迷宫区完成事实使用 `saodg:run_completed` 等独立类型与唯一factId，包含runId、玩家UUID、迷宫区ID、难度、结果版本。脚本以该事实驱动专门的迷宫区任务。

首次通关类目标可通过“已达到目标状态”幂等更新。计数任务需接收方保存factId回执或查询SAODG已完成局集合，不能每次事件回放就简单 `+1`。

FTB队伍与SAO社交队伍不是同一权威：参战资格取SAODG固定名单；FTB共享目标按接收时的明确政策更新。首发个人通关记录保存个人；若给FTB队伍计数，必须在完成时固定目标TeamData身份并定义后续换队行为。

同类型迷宫区怪可能仍增加原版击杀统计，既有FTB任务也可能直接监听Forge死亡；因此首发尽量使用 `saodg:*` 自有怪物，并审计任务筛选。不能仅加一个KubeJS `return` 就承诺所有旧任务完全不受迷宫区击杀影响。

## 10. 兼容验收与发布产物

发布兼容脚本前运行静态仓库现有的NPC、Hub、任务历史和任务线验证，并追加SAODG过滤与事务检查；现有验证命令由该仓库 `AGENTS.md` 指定。Node通过仅说明脚本隔离检查，不代替Forge行为验收。

正式包包含SAODG JAR、兼容脚本补丁清单、配置/地图版本清单和操作文档。启动输出适配器选择、哈希基线和探测结果；不记录账户密钥或玩家完整NBT。

验收门槛：无SAO/KubeJS可独立启动；目标整合包可联机；濒死、召唤归属、数值、旧奖励、旧任务、重复领奖与保存恢复全部有明确测试记录。具体检查见[验收计划](ACCEPTANCE_PLAN.md)。
