# NBTCreator 三级代理信息包、提示词与引擎反馈设计

**状态**　审阅稿。补充主方案的任务签发、局部读取、文件归属和反馈协议。 [主整改方案](2026-11-24-authoring-workflow-remediation.md)

**核心决策**　一级保存整栋决策，二级只接区域简报，三级只接一批相关构件的任务和局部证据。参考图和方块都可按需取用。引擎执行范围、来源、旧值和发布校验。单件家具沿用构件入口，需要装入现有建筑时走局部编辑，多区协调时才进入三级编排。

## 1. 任务分流与最短路径

| 用户需求 | 入口与最小输入 | 结果与检查 |
| --- | --- | --- |
| 单独做一张桌、一个柜或一组可独立复用的桌凳 | **构件路线。** 给用途、尺寸、朝向、风格和可选参考图。从现有构件、配方或 `WorkingModel` 构件入口生成。 | 构件几何、合法方块状态、尺寸、支承和适用预览。可按原方式保存。 |
| 在已有炉厅增加一组桌凳，或只修一处柜门 | **选区路线。** 锁定宿主源、局部范围、支点和附近必要路线。复用 `selection-edit context/compile` 或 `WorkingModel.patch`。 | 只读局部、候选和差异检查，复验受影响站位。按已有宿主另存流程保存新制作版。 |
| 多个房间分给不同代理，或需要统一楼板、梯口、区间接口 | **协作路线。** 在同一制作运行中登记源、分区、接口和构件工作包。可以从现有制作版直接进入，也可以从图像引导规划开始。 | 按组局部读取、提交、跨区复验，由一级原子发布一个整栋子版本。 |
| 用户要求先出图再建模，或指定三级分工 | 按用户指定的阶段和分工安排。独立构件也可先出参考和局部预览。 | 按实际要求登记图片及所用机位，权限和存储仍沿对应路径。 |

分流依据是交付对象、现有宿主和共享接口风险。做多件家具可以只是构件批处理。一个场地内的一组家具可以只是一次选区修改。单个构件可以产生整体效果，但生成器只算实际构件或宿主局部的几何。产品首期复用这些已有入口。[构件配方](../../../.agents/skills/minecraft-nbt-modeler/references/parametric-components.md) · [选区编辑](../../../.agents/skills/minecraft-nbt-modeler/references/selection-edit.md)

**验收断言**　“做一个 3 × 1 × 2 格的木桌”在离线构件路线完成。合成测试确认该用例无整栋生成调用、无制作运行工作包、无图生要求，构件验证与按需预览都可用。放进既有室内时加上宿主源和局部保护即可。调用者可以主动升级到协作路线。

## 2. 三级输入矩阵

| 信息 | 一级主代理 | 二级区域代理 | 三级构件代理 |
| --- | --- | --- | --- |
| 任务目标 | 用户意图、必要与可选范围、拟交付物、整栋成败条件 | 本区用途、行为顺序、该区必做项和允许延期项 | 一批构件的用途、主次、完成清单及可独立判断的验收条件 |
| 空间 | 整栋粗布局、楼层、朝向、全局坐标、区域编号 | 本区尺寸、楼面、入口、可写盒、保护、邻区接口和动线 | 局部原点、允许写入的盒、只读邻域、支点和玩家脚位 |
| 图像 | 图集索引、来源、采用/校正记录，按视角展开 | 本区相关外观或室内裁片，必要时一张邻接图 | 使用侧或装配近景，通常先发一个相关裁片 |
| 真实方块 | 读取整栋摘要，按冲突和验收范围展开 | 接口和主要通路摘要，按工作包请求局部 | 只读区分页，写点、支点、相邻地面及必要空格，含方块状态和墙层 |
| 材质与约束 | 全局风格、必要材料角色、工作区和发布规则 | 本区用材和少量已定共用细节，已冻结的硬限制 | 材质角色、可采用的原版状态、与当前家具有关的禁改坐标和预算余量 |
| 结果与进度 | 各区完成度、关键阻塞、跨区边界、发布证据 | 模块是否齐、候选差异摘要、冲突部位和预览 | 实际改点、该构件是否站得住及对应的错误和修复项 |

首轮包默认给够开工的语义摘要，按 `section` 或引用 ID 请求放大的内容。语义简报、机器几何、参考图分通道传递。长状态串、调试堆栈、其他包完整补丁和历史全过程留在可定位的本地证据。硬约束始终随当前包生效，由引擎在提交和合模时完整核对。首期先统计各层实际传输量与往返次数，按样例调整预算，避免把经验文字上限当成硬门槛。

### 2.1 一级如何签发给二级

一级在工作包中给出本区的交付边界。例如“炉厅完成用餐、备餐与取柴，主过道和梯口保持可走”。加上空间 ID、角色说明、区域和共享楼板的坐标、优先参考图角色、出入口及预期审阅视角。全局但必须传达的约束用实际生效值，如本工程的方块版本、墙层保留、门洞净空和可用材料。其他房间提供简名与接口用途。

二级回传一份区域承诺清单和若干构件批次。一个批次可以包含桌、凳、桌巾、餐具等相互依赖的配套。把跨区公共结构或者无法明确所有权的位置交给一级调解。二级检查是否覆盖各用途、支承和相邻路线，汇总已完成项与阻塞坐标。

### 2.2 三级最小工作包

三级看到一个简报头、一组按需引用和一份可查询的包契约。以下是面向模型的投影视图，坐标和字段做法用合成示例表达。机器提交字段以实际 `tool-catalog.json` 为准。

~~~json
{
  "package_id": "hearth_dining",
  "package_revision": 2,
  "parent_id": "ground_hall",
  "goal": "做一组能落座的旅店餐桌，实景可辨桌脚和成组桌上用品",
  "component_ids": ["long_table", "side_benches", "table_settings"],
  "required_checks": [
    "桌沿下有可辨桌脚，凳子朝向桌面",
    "门侧通道与指定脚位留空"
  ],
  "write_boxes": [{"lo": [28, 2, 23], "hi": [34, 4, 27]}],
  "reference_refs": ["inn_detail:trestle_tables"],
  "read_refs": ["dining_floor", "east_aisle_edge"],
  "interface_refs": ["ground_to_stair"],
  "required_view_ids": ["ground_dining_detail"]
}
~~~

取用约定：

- **先读摘要。** 阅读用途、写权限、坐标方向、邻路和期望轮廓。没有完整参考图时，可用已标注的裁片。没标定的透视图只用来理解可见部件。
- **读取写点和依赖点。** 请求 `authoring.context` 对应页。以全局 XYZ 整数包围盒表示读/写区，端点包含。裁片则是像素半开边界。局部摘要里的 `origin` 用于一次转换，后续提交采用全局坐标。只在当前页定义的范围内将未列出的方块解释为空气，页外状态保留未知。
- **按构件留痕。** 先确定主体、承托、接合和使用侧，再按实际形状选楼梯、半砖、活板门等状态。回传构件 ID、改动和可核验接点。整个批次可一起交付，便于父级检查是否缺了配套。已经符合要求的构件可记录现状证据，由父级决定是否需要新增补丁。首期现有提交接口要求有实际差异，零改动的证明走观察回执或作为后续显式能力。
- **确认读取与视觉证据的边界。** 当前实现中的 `read_sha256` 绑定包、修订、源和读盒。它证明内容来源一致。若要限制必须读到的安装面，应由引擎按相应 page 签发读取回执并引用每个必要页。实际看图继续用带画面位置的观察登记。

现有 `authoring.inspect` 的紧凑视图面向运行概况，`full` 面向整栋核对。增加给区域和构件的投影时，应从已登记的包 ID 派生只读视图，通过对应租约返回当前包。读取结果以源与包修订为键，可在一次请求内复用模型加载。收到 `CONTEXT_LIMIT` 时回传具体页与建议缩小的边界，重新签发后更新读取指纹。

## 3. 三套提示词

提示词从已验证的工作包和共享模板组装，CLI、桌面和外部宿主调用同一组字段。固定顺序是角色与交付、有效约束、任务摘要、相关引用、可调用工具及返回结构。文件正文、参考图文字和其他代理汇报都作为待审数据，任务权限采用引擎签发值。

### 3.1 一级主代理模板

~~~text
你负责整栋建筑的用途、区域连接和候选合模。
先把 {用户意图}、{已有模型与参考} 和 {硬约束} 落到空间承诺。
写清每区的用途、入口、必要路线、公共结构与验收条件。
给二级签发区域简报、写区、只读邻域与接口。只打开解决当前决定所需的参考图。
接收各区回执后，处理跨区冲突，以同一基线原子预检候选。
核对真实路线、接口两侧和必要实图，并保存一份可审阅的整栋制作版。
交付分区表、未解决问题、实际图像与源文件引用。审批和导出按已有入口办理。
~~~

### 3.2 二级区域代理模板

~~~text
你负责 {区域} 的完整用途和本区构件协作。
已签发范围为 {区域授权}。先看 {本区要求与接口}，再决定构件组。
按玩家会做的事情组织构件包，每个构件写用途、落点、承托和验收视角。
把共享支点、必经路线和配套关系交代给三级代理。一个包可以包含多件相关构件。
核对返回的旧值补丁、局部站位和实图，记录遗漏项和该区与邻区的影响。
回传区域概要、候选哈希、阻塞和已核对的位置。需要跨区改动时交回一级协调。
~~~

### 3.3 三级构件代理模板

~~~text
你负责 {构件列表}，使用同一个已冻结宿主和局部范围。
先读 {方块页}，查明旧状态、墙层、支点和要保留的空气。
按使用侧和装配顺序设计主体、承托、接头和薄面。参考图用于确认所见轮廓。
新状态用 Java 1.20.1 的合法方块状态。每个写点回传全局坐标及 before/after。
按构件回传完成情况、接合点、玩家站位及需要从哪张图复验。
收到反馈时优先修相关构件和实际坐标。接口或来源有变化时重新读对应页。
~~~

返回模板应要求可验证的材料决策与证据，例如说清柜门的铰向和它紧贴的箱身坐标。上下文不足时返回具体缺项，例如“缺少楼板下一层的机位及落脚面”。避免通过一段抽象长文替代实际数据和安装证据。

### 3.4 同一 CLI 的按工作包暴露范围

三层共用同一个 CLI、工具目录和 Python 引擎。协作工作包的提示词只列当前层级和当前包可用的动作。角色从已登记的工作包及认证会话解析。CLI 参数、提示词里的自报角色和用户提供的输出字段都属于请求数据。

| 层级 | 默认工具入口 | 执行时的范围 |
| --- | --- | --- |
| 一级 | 整栋摘要、来源绑定、区域签发、合模预检、整栋审阅、保存制作版 | 用根包或既有人员授权校验整栋操作。发布前继续核对父版、候选集合和建筑锁。 |
| 二级 | 本区简报、接口读取、签发本区构件包、候选摘要及区域反馈 | 只可派发到已授权的区域及子包。子包读写范围以父包授权为上限。 |
| 三级 | 领取和续租本包、读取本包方块页、查合法方块状态、生成局部预览、提交本包补丁 | 读页及预览绑定本包和其授权源。局部预览的主体及输出限于授权范围和本次尝试。正式发布、全量运行明细和向下派发按权限拒绝。 |

命令发现和动作校验分成两处。工具目录保留完整公共定义，提示词与宿主工具面板根据受信的包上下文派生一份可用动作清单。执行端按同一会话核对包、租约、修订、来源和读写权限。给三级藏起一级命令只能缩减上下文，提交和发布仍须独立检查。整幅模型预览如果确有必要，由父级生成并分享相关机位或裁片。对普通 CLI 的路径校验和危险动作限制沿用现有逻辑。

受限代理从宿主入口进入协作工作包。需要进程级隔离时，宿主只提供中介 CLI 动作、获准的输入和本包过程目录。共享同一个可任意读写工作区的 shell 时，CLI 权限约束适用于经该接口的操作。引擎授权不替代文件系统访问控制。个人执行独立构件、普通选区编辑和维护命令时，按各自现有入口运行。

首期优先复用工作包现有的领取、读取和补丁提交动作。若局部预览目前只能接收任意整栋源，则先由父级出图，再增加能核对包绑定的局部预览入口。命令清单刷新时读取当前修订，租约失效或包关闭后提示接续动作。

### 3.5 按工作包选择模型与升级条件

模型由发起请求的宿主选择。内置 AI 可在已有请求调度处接入，外部 Agent 使用自己的宿主能力。引擎提供工作包类型、参考图需求及结构化验证结果。换模型继续沿用同一个包、源绑定和工具权限。首次实现用可配置规则，积累本项目试验数据后再决定是否训练路由器。

| 情况 | 调度规则 |
| --- | --- |
| 尺寸、朝向、支点和目标都明确的摆放、改色、配套家具 | 先用经济档。要求具备结构化补丁输出，必要时能读取该包引用的图像。可复用配方的固定部分先由引擎执行。 |
| 参考图歧义、必须解读细图、复杂轮廓，或跨区共享支点 | 在首轮选择具备相应视觉或空间推理能力的模型，或者先由二级把图像目标和支点转成可检查的规格，再把有界补丁交给经济档。 |
| 候选漏项或局部形状失败，反馈能定位到具体格和构件 | 经济档按错误和实际状态做一轮小范围修订。重复同一问题或质量评审仍未达预设条件时，升级模型或退回二级重新界定工作。 |
| 源或租约已失效、权限不足、参考缺失、碰撞形状超出引擎覆盖 | 先修复来源、授权或验证条件。模型升级不解除引擎阻断。 |

经济档或高能力档是工作区配置的档位。档位切换和至多几轮重试由任务预算控制。日志记实际模型、任务类别、选择原因、是否需图像、尝试次数、升级原因、模型账单、引擎校验时间和人工复核时间。失败包的花费也算进总成本。首轮并列比较经济模型固定、较强模型固定、经济优先且失败升级三条路线。保持同源、同工作包、同验收脚位和画面要求，报告首轮通过率、最终通过率、每验收通过包的总推理成本和人工复核分钟数。对照中的成本下降以本项目实测为准。[FrugalGPT](https://openreview.net/pdf/3bc37598b9fc1a12afe49c84e43e6beb9d8e2c6a.pdf) · [RouteLLM](https://arxiv.org/abs/2406.18665)

## 4. 文件耦合、任务树与版本链

### 4.1 三种关系各有职责

| 关系 | 由什么管理 | 示例 |
| --- | --- | --- |
| 代理任务树 | 一个制作运行的工作包清单，使用 `parent_id`、`depth`、包修订、租约和不可变候选哈希 | `root → ground_hall → hearth_dining` |
| 建筑版本链 | `WorkingModel.save_draft`、发布锁、SNBT 父版本、模型及墙层指纹。历史需要时由现有独立 Git 历史库存档 | `master v0 → master v1`。两批都由一份 `v0` 派生，合入后只发布一个 `v1` |
| 软件源码开发树 | 软件仓库的 Git 分支、独立工作树、提交和测试 | 工作台、共享引擎和新协议在实现工作树中开发 |

现有试作按位置和基线哈希合并了多个局部文件。整改工作树的 P0–P2 草稿已把委派和候选元数据保存在批次 run 的 `authoring.json`，同一运行锁下由引擎原子写入。历史归档使用创作工作区中独立的 `.nbtcreator/history/repository.git` 及内容对象库。三级任务深度与建筑版本在数据中引用，工作包数量和 Git 分支数量互相独立。[现有批次结构](../../../.agents/skills/minecraft-nbt-modeler/references/batch-workspaces.md) · [建筑版本历史](../../../.agents/skills/minecraft-nbt-modeler/references/version-history.md)

### 4.2 推荐的文件归属

~~~text
创作工作区/
  nbt_models/<建筑>/<制作版本>/
    master/model.snbt
    coordinates.json
    model-version.json
  nbt_models/_workspaces/batches/<批次>/runs/<运行>/
    authoring.json                  引擎持有的运行状态、工作包关系与候选索引
    references/                     可选导入副本及角色清单，使用相对路径与哈希
    artifacts/<包 ID>/<尝试 ID>/     该包的报告、补丁备份、取证图，按次写入
    candidate-<合模哈希>.snbt         预检候选
    reviews/<审阅修订>/              基线与候选绑定、相机、图像、检查和观察
  .nbtcreator/history/              已发布版本的历史索引与内容对象
~~~

目录里的 `references/`、`artifacts/` 和 `reviews/` 是建议布局。已登记在工作区其他位置的本地图可以通过路径和哈希继续引用。首期内嵌补丁与候选哈希可以保留。体量需要时再把大补丁移到内容寻址文件，由 `authoring.json` 引用，避免提前引入多份状态。

- 一级经引擎修改运行、选择候选和发布主版本。二级经引擎向区域报告和本区子包签发记录写入；三级可写自己的过程文件并提交候选。注册后的证据以新修订补充，历史引用持续可核对。代理各写各的尝试输出，运行清单由引擎在锁内原子写。
- 所有几何写权通过 `write_boxes` 和保护区表达，文件归属另由包与尝试 ID 表达。共享的只读楼板可以出现在两包的读取页中。对同一实际方块有安装需求时，由上级重分范围或另发接口任务。
- 若代理进程在独立目录运行，交接包通过受控工作区收集相对路径、源指纹和候选散列。接收端验证范围、租约、旧值和原路径绑定后登记，避免依靠同名文件、时间戳或 Git 文本合并推断几何关系。
- 工作区迁移时保留 `nbt_models/` 和已有历史对象。发布后旧尝试归档可按项目策略保留；任务日志和临时产物遵循项目约定。租约令牌只进工具调用，简报、图册和公开回执只呈现脱敏状态。

工作包投影和提交范围用于约束接口和工作量。代理进程对操作系统文件的访问仍由宿主控制。主版本发布时继续独立核验基线、墙层、实际差异和引擎证据。

## 5. 引擎反馈如何返回

### 5.1 统一的反馈形状

引擎沿用结构化错误和增量诊断。每条问题包含稳定 ID、阶段、代码、可证明的结论、负责工作包、涉及部件/路线/机位、坐标或边界、证据和下一次复验条件。紧凑反馈回显已检查数量、阻塞数和优先项，可展开到全部问题及报告。前置约束、旧值和源校验是确定性检查，材质、视觉遮挡和主题完成度需要对应证据。

~~~json
{
  "issue_id": "ground_hall/ceiling_at_guest_rug",
  "stage": "whole_review",
  "status": "needs_review",
  "owners": ["upper_level", "ground_hall"],
  "affected_views": ["guest_furnishings", "ground_dining_detail"],
  "region_hint": "楼板上表面与一楼可见顶面",
  "evidence_ref": "reviews/example/floor-sides.json",
  "next_check": "同时复看地毯与楼下顶面，重跑原走线和脚位"
}
~~~

### 5.2 发送到哪一级

| 现象 | 优先接收者与返回内容 |
| --- | --- |
| 方块状态错误、写区外、触及保护、旧值不符 | 三级收到包、格点、实际值和应有范围。使用已有错误语义，如 `WRITE_OUT_OF_SCOPE`、`PROTECTED_POSITION`、`PATCH_BASE_MISMATCH`。必要时提示重读指定页。 |
| 兄弟写区交叠，两批共享支点被改，侧面读取超授权 | 二级收到两包 ID、重叠范围或被改支点。`WRITE_SCOPE_OVERLAP`、`PATCH_OVERLAP` 和 `READ_DEPENDENCY_CHANGED` 可定位到具体坐标。二级重新分配接口或把问题申报给一级。 |
| 源或父版本变化、需要跨区修改、房间关键路径回归 | 一级收到父源与当前版本、受影响区域、路线 ID 和建议重签范围。`STALE_PARENT` 等错误保护现有 head。一级决定取舍和回装。 |
| 碰撞形状未知、搜索预算用尽、柜台站在错误操作侧 | 返回明确的覆盖不足或实际错误，列出方块形状、失败姿态与可用的复查方法。可达结论不能覆盖操作侧检查。 |
| 图像成功生成、未实看，或前后机位/光照不同 | 审阅显示待观察或不可作为同机位对照，允许在后续复拍。视觉闭环记录具体所见、坐标和机位。游戏运行与静态检查分别返回证据。 |

### 5.3 返工与节制

- 技术性中断可以按现有幂等语义用同一请求重试。新意图和新修订用新请求。作废的租约、变化的读区和新的父版本促使重新读取、签发及复验。
- 明确的局部问题优先退到能修它的一层。比如柜门朝向错误，三级只读箱身和接点。地毯露到楼下时，二级或一级给卧室和炉厅各补一张实际同机位，并协调修改楼板或表层饰面。修完只更新受影响的证据，并执行整栋声明的必要检查。
- 经过生成、参数化的自动化可以给出尺寸、接触盒和可能受影响的视角。由审阅者从落盘实渲染确认地毯露色、家具过少、支托看起来断开这类视觉现象。预览图本身可核验像素与来源，观察行为由实际审阅角色登记。

## 6. 实施顺序和验收

| 阶段 | 验收用例 |
| --- | --- |
| 短路线保持 | 独立桌子可以离线生成和局部验证。安装一组桌凳时只读其宿主局部。旧的构件、选区和制作版入口可正常使用。 |
| 分层信息 | 一级简报含整栋约束。二级只投影本区与接口。三级默认只返回已授权的本包及指定读取页。展开引用可补资料。读取页误用、权限交集为空、额外字段和令牌误入简报等反例需显式处理。 |
| CLI 按包暴露 | 同一 CLI 的协作任务按已登记角色生成动作清单。三级能读取自己的页并提交合法补丁，手动请求兄弟包读取、全量查看、派发或主 SNBT 保存时由后端拒绝。二级越出本区签发也拒绝。独立家具仍可直接走构件 CLI。 |
| 两批家具 | 一份普通 SNBT 由一级分区、二级同次签发、三级两批各做多件，保留两个候选及清单，原子合出一个版本。父源、旧值、只读依赖或可写盒变动均有可定位反馈。 |
| 跨层审阅 | 楼上加入着色整格地板，影响清单能指出楼下顶面。由实际图发现后补做该侧修订。上下层机位、旧站位和必要路线经复验。 |
| 重启与恢复 | 引擎中断后可恢复工作包状态，旧租约提交被拒绝。同一请求返回同一候选或新版回执。用户已另存时保留胜出版本。 |

落实顺序为短路径与角色投影 → 三级提示词及分页读取 → 分层反馈和真实审阅。优先扩展已有 `authoring.inspect/context/submit`、`selection-edit` 和诊断回执。新运行格式若需增加角色投影、页回执或工单证据字段，按加法兼容补齐 schema。桌面最后消费同一个契约。

首轮记录材料交付数量以外的指标，包括每层传输字节、实际读取页、引用展开次数、首个问题定位耗时、修复局部的重读次数和人工看图耗时。用相同场景与改动预算比较全量上下文和最小包，在保持完整性、路线与支点证据的前提下判断是否节省信息。对旅店“是否应加近景”独立继续使用主方案的四组对照。

**建议转发给实施会话的摘要**　保留现有构件和选区短路径。三级制作只用于需要协调多区的场景。一级、二级、三级分别获取整栋、区域与构件投影，读取页与实际写权限绑定。用现有 `authoring.json` 维护任务树，候选和审阅附件按工作包分目录，模型版本继续从主模型发布锁管理。先补齐炉厅等合成夹具的最小信息和权限回归，再接入上下层复验、同机位图和 UI。

## 8. 从图片效果到可搭建的 Minecraft 构件

先区分用户要从图片保留的内容。对于木构旅店，这可能是深色窗洞、层层托木和出挑的层次。对于概念壁炉，这可能是石框包裹的深炉口、暖光集中在下部。每个有辨识度的效果写成一个构件要求，再和当前尺寸、朝向、方块权限绑定。

1. **提取可检验的视觉线索。** 列轮廓、厚度、前后层次、重复节奏、明暗关系和使用侧。单张图看不清的深度、背面及承托方式记录为设计补全。有正交视图和尺度锚点时用现有标定方法建粗形。
2. **先定体量和留空。** 写明投影尺度、窗洞或炉口大小、玩家站位、相邻承托和哪一侧能看到出挑。先用整块得到大轮廓，再解决小部件。
3. **提出少量原版组合。** 代表构件可以比较两个合法候选，统一占用边界。比如凸窗用后退一格的玻璃和细窗棂制造阴影，窗台用半砖薄边，托木用有朝向的楼梯及原木接到腰梁。强调窗深和支承的 A 版与强调细窗格的 B 版都登记各自的取舍。材料按木架、填墙、玻璃和阴影区成组选择。
4. **技术检查后观察实际渲染。** 核对合法状态、真实接触、墙层保护及必要通路。正面检查轮廓和节奏，斜侧核对窗深、托底和遮挡，玩家机位检查用途。参考图复现可比较相近观察角度。修改效果比较固定同一相机和光照。补拍视角继续保留各自的证据身份。
5. **按目的挑选或再改。** 用参照效果的可辨度、厚度与接合、玩家可用性分项评审。在满足必要约束后由作者确认一种做法。优质的楼梯、半砖、托木组合可以登记为以后复用的配方。

首轮可用凸窗、弯弧冷却塔和带暖光的石炉三个样例。对比直接用参考图生成与使用“效果描述、可用部件、实际支点和机位复验”的两条路线。保持相同模型、现有宿主与修改预算，分别评审意图相似度、合理变体与方块状态合法性。用同一盲评条件确认变化是否有意义，并记录无法从图上判定的部位。这个实验与 `3.5` 的模型档位试验分开进行。
