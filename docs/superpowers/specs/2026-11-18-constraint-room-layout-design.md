# 「我的项目 → 约束 → 房间」文件布局审查稿

## 用户确认的范围

- 建筑库和创作方案以「我的项目 → 约束 → 房间」组织。界面的项目标题固定显示「我的项目」。
- 正式文件结构也按约束归属存放房间。约束集中保存在项目顶层，通过读取真实文件显示和管理。
- 「起草要求」阶段即可勾选约束。已选规则进入 AI 起草、审查和交接，已有方案按保存的版本恢复引用。
- 「房间」沿用当前建筑库的独立条目含义。同一房间下可以有多个制作版。
- 旧项目由 `tools` 中的脚本迁移。设置页提供下载、预检和调用迁移工具的入口。

## 建议的存储方式

单项目工作区以 `nbt_models/` 为项目顶层。一个工作区有多个项目时，各项目以自己的目录为顶层，各有一份活跃约束库。例子中的 `Kuuu` 是现有规则，房间名称用占位符表示。

```text
nbt_models/
├─ 约束/
│  ├─ .layout.json                   目录格式版本
│  ├─ Kuuu--<约束ID>/                  Kuuu 归属目录
│  │  ├─ 约束.json                   规则正文、适用范围、当前修订
│  │  ├─ 历史版本/                    每个修订的独立快照
│  │  └─ 房间/
│  │     └─ <房间初始名称>--<房间ID>/
│  │        ├─ 房间.json              房间编号、归属约束、其他约束引用
│  │        ├─ 提示词方案/
│  │        └─ versions/
│  │           └─ <版本>/master/model.snbt
│  ├─ 门洞规则--<约束ID>/
│  │  ├─ 约束.json
│  │  └─ 历史版本/
│  └─ 未归组/
│     └─ 房间/
├─ _migration/                        已执行的迁移记录及旧路径映射
├─ _workspaces/
│  ├─ project_design/约束/            工作区共用规则目录
│  └─ 方案草稿/                        尚未登记到房间的方案
└─ _exports/                           交付产物
```

每条约束独占一个目录，`约束.json` 保存 ID、名称、适用范围、当前修订和规则正文。约束范围可以是项目共用、指定归档形状或指定房间。目录由创建时的可读名称和稳定编号组成。规则和房间改名后，标题从元数据读取。

房间的 `房间.json` 保存归属及引用的约束 ID。某条约束第一次收到房间时，才创建它的 `房间/`。跨项目共用规则集中在工作区的 `project_design/约束/`，迁移时可保留旧格式和历史快照。

每个房间有一个稳定编号和一处实体目录。归属从本项目的已选约束中指定。只有一条可归属约束时将其作为默认，未指定时用「未归组」。工作区共用规则可参与引用。起草和自动保存使用方案记录，可以改名、改勾选或调整预定归属。点击「登记房间」或「确认并交接」时登记房间并确定制作输出路径，方案沿用同一编号归档到房间。

房间可同时引用多条规则。在其他规则的房间列表中以同一个编号定位。调整引用和调整磁盘归属是两种操作，后者进入单独的整理流程。归属所用约束可以归档，归属目录继续可读，已有方案可读取原快照。

## 数据归属与模块分工

| 模块 | 读取和维护的数据 | 提供的能力 |
| --- | --- | --- |
| 约束库 | 项目顶层约束、工作区共用约束、规则修订 | 按项目、形状、房间匹配规则，给出适用范围和冲突原因 |
| 房间库 | 房间编号、显示名称、归属、引用，以及现有版本元数据 | 按编号找房间和版本，登记房间、保存引用、整理归属 |
| 建筑库索引 | 房间库和约束库的读取结果 | 生成目录树和规则的反向房间列表。可丢弃并重建的缓存只用来提速 |
| 创作方案 | 房间编号或新房间的预定归属、已选规则快照 | 起草、审查、交接共用当前勾选。旧方案的引用版本由方案快照提供 |
| 迁移工具 | 旧数据的只读清单、预检决定、目标进度及路径映射 | 使用约束库和房间库的公共解析与写入规则，生成并验证独立副本 |

房间引用关系只在自己的 `房间.json` 中维护。其他约束下的房间列表由索引反查。改约束名称时写约束记录及对应修订。增减已登记房间的引用时写房间元数据。起草页面改勾选时保存当前方案，已有房间的长期引用由「房间管理」独立维护。整理磁盘归属时，经确认移动房间目录并刷新路径索引。约束历史、AI 输入和交接都使用冻结快照，房间移位后仍能按编号和路径映射校验旧源文件。

源码分工如下。

```text
NBTCreator/
├─ .agents/skills/minecraft-nbt-modeler/
│  ├─ scripts/
│  │  ├─ nbt_constraints.py     约束库、修订、适用性和校验
│  │  ├─ nbt_rooms.py           房间归属、引用和版本定位
│  │  ├─ nbt_detail_control.py  建筑库索引和模型展示接口
│  │  └─ nbt_prompts.py         草稿、约束快照和交接归档
│  ├─ prompt-console/           起草和审查共用的约束勾选
│  └─ assets/viewer/            建筑库树和设置界面
├─ desktop/                     工具下载校验、后端调用及进度桥接
└─ tools/constraint-room-migration/
   └─ migrate.py                预检、迁移、验证
```

现有编目和新建归档会根据归档形状推算目录。新布局把目录分配和定位交给房间库，编目、创作方案和制作版保存复用该解析。桌面、CLI 和 Agent 共用相同的规则接口。旧快照原有的路径字段与哈希保持可校验，历史文件通过映射定位。

## 读取和编辑

打开项目时按约束目录和房间元数据读出树形目录。起草页先请求规则摘要，点开要求或勾选时再请求完整快照。后端重复查询可利用进程内记录缓存，历史修订按需访问。归档形状从房间或版本元数据读取。桌面界面、CLI 和 Agent 共用解析和写入逻辑。

房间当前的归属和引用以房间元数据为准。经验证的已保存方案显示在历史引用中。按形状找出的候选只出现在「可关联」。从某条规则下起草，会在「建造想法」上方显示并预选这条规则。为已有房间新起草时，用该房间当前引用的 ID 读取现行规则，按房间专属、形状、项目共用顺序处理兼容性。起草、审查、交接共用一组勾选与快照。规则更新后可显式改用新版本，保存过的方案恢复原勾选和带哈希的快照。有效归档形状、参考尺寸和固定尺寸按规则来源展示。

## 旧数据与迁移

新布局读写独立目录。旧布局继续读取根层 `项目约束.json`、形状和建筑子目录的约束文件和工作区共用记录。根层规则可在起草页直接勾选。旧项目迁移使用独立副本，界面验证通过后可选择打开副本。

迁移预检列出规则及其原范围、房间与版本、已有引用、预计新路径、重名和未归属项。每个房间只有一个明确目标目录。明确归属可沿用，历史方案中的引用作为建议，预检可逐项或批量确认。待确认和存在冲突的归属暂列「未归组」。规则 ID 与历史修订保留，新的集中记录附带原范围。历史约束快照原样归档。对旧文件路径登记到新路径的映射，按版本和原哈希核对后用于历史浏览、任务读取和备注。几何、历史方案正文、交付回执及其哈希作为验收基线。绑定旧位置的任务需要保持可验证，重新执行时按现有流程重新准备。

试迁在独立副本完成。预检冲突与中断都可恢复。切换工作区前校验房间及版本计数、SNBT/NBT 哈希、缩略图与预览、标注、方案快照、已交接任务、继续保存和显式导出。复跑预检和试迁不会为同一个房间再复制出第二份实体。通过桌面和 Agent 两条入口验收。

## 迁移工具与设置入口

迁移工具放在 `tools/constraint-room-migration/`，由官方发行流程作为独立资产发布。脚本提供预检、迁移、验证三个入口，命令行和设置页调用同一份实现。工具声明版本和可处理的数据格式。设置页复用应用的官方下载来源，从可信发布信息校验 SHA-256 和工具与当前应用的兼容性，再在独立的工具缓存中准备运行。

在「设置 → 项目与文件」打开「旧项目迁移」。流程如下。

1. 选择旧工作区，再选目标工作区。默认将旧项目迁移为一个独立副本，目标和来源须明确分开。
2. 点击「下载工具并预检」。已有校验通过的兼容工具时复用缓存。脚本通过现有后端的专用接口运行，只读预检先列出待迁移的规则、房间、版本、磁盘用量、建议归属以及冲突。
3. 在预检结果里确认归属和目标位置，再点「开始迁移」。通过校验的输入写入目标副本，保留迁移进度和路径映射。中断后先核对已有结果，再继续剩余项。
4. 验证模型、版本和历史引用后，显示报告和「打开迁移后的工作区」。用户通过这个入口切换。预检失败、空间不足和来源变化时停在对应步骤，保留错误详情供处理。

设置页传入经确认的工作区路径和迁移阶段。下载位置、工具入口及可用命令由应用后端确定。脚本、用户项目路径和进度记录各在对应目录。

在 NBTCreator 源码根目录也可以用 mise 调用脚本。`plan` 将预检结果写到标准输出。将该 JSON 对象放在请求的 `plan` 字段，再用 `owners` 将房间 ID 映射到同项目约束 ID。留空的房间进入「未归组」。`apply` 输出校验结果，`verify` 可再次核对目标副本。

```powershell
mise exec -- python -B tools/constraint-room-migration/migrate.py plan --source D:/Work/Old --target D:/Work/Migrated
mise exec -- python -B tools/constraint-room-migration/migrate.py apply --request D:/Work/migration-request.json
mise exec -- python -B tools/constraint-room-migration/migrate.py verify --target D:/Work/Migrated
```

## 交付顺序与边界验收

1. 先打通根层约束读取和起草勾选。用现有根层的 `Kuuu`、独立形状和已登记房间各验一遍。
2. 接入房间库和真实目录布局。验证同名房间按编号区分，改名称、改引用和改实体归属各走自己的操作。
3. 接通设置中的下载、预检、迁移和验证。在副本验收重名、中断恢复、版本和旧引用。迁移工具与应用都用同一条源文件校验链。
4. 清空可重建索引后重新读取文件，目录树、房间引用和版本数一致。桌面、CLI 和 Agent 三条入口的可选规则和冲突结果一致。

## 审查时要定的规则

1. 一个房间只有一条实际归属约束，可同时引用多条规则。起草可改预定归属，登记房间或首次保存制作版时才落盘。
2. 改规则名更新显示，改房间磁盘归属走单独的整理确认。
3. 旧工作区从副本验收，预检确认旧房间的物理归属。历史引用提供建议，待确认的房间暂列「未归组」。
