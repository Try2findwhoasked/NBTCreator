# 外置知识库与网络搜索设计

本方案用于 NBTCreator 下一轮开发。目标是让 Agent 和桌面端在同一个参考入口查到经过定位的资料，把选中的局部证据带入创作，事后能说清楚它支撑了哪项建模决定。默认离线，只有当前任务明确要求或用户主动发起时才联网。

## 当前基础

- 建筑书库使用 `books.json` 与 SQLite FTS5 按章离线检索，查询会回源校验原文哈希和命中行。`retrieve architecture --library ...` 能用，但结果还不能直接进入桌面端和 Agent 共用的 `retrieve bundle/read`。
- 共用入口已有 `retrieve search/source/bundle/read`，支持工作流内选定的资料和适用的构件。对外 Agent 的知识组、桌面内置 AI 资料和建筑书库各自管理。当前桌面默认摘录另走 Node 逻辑，显式选集则由 Python 校验。第一阶段沿用这些设置的权限边界，把新增资料接到显式选集路径。
- 在当前 15 本书的索引上，`飞扶壁 尖拱` 和 `flying buttress pointed arch` 的前三条一致。`玫瑰窗 放射式` 返回零条，`rose window tracery` 返回三条。建筑书库与引用集合的 10 项引擎回归、2 项 Node 来源与发送范围回归均通过。这是实施前基线，三条结果中是否适合具体建筑需复核。

## 资料分工

| 资料 | 来源与用途 | 使用入口 |
| --- | --- | --- |
| 工具规则与项目要求 | 工具目录、已启用的工作流说明和当前用户要求决定字段、操作和项目边界 | 生成的 Agent 入口与 `capabilities` |
| 建筑参考 | 已连接建筑书库、自选 Markdown/TXT、许可允许的公开资料。提供构造做法、历史事实和设计线索 | `retrieve` 与现有参考选择器 |
| 构件资产 | 已验证的配方、固定构件和可复用几何。保留资产来源及版本校验 | `asset-libraries` 与原预览、放置入口 |

来源按用途分别判定。核对建筑年代时先看原建筑管理方、文博机构或研究者的原始资料。核对 Minecraft Java 1.20.1 中的方块状态和工具参数时，以版本对应的本地注册表、引擎及实际检查为准。资料作为引用内容传入，网页、书籍和图片说明中的指令没有权限改变工具、用户约束和交付阶段。

## 一、外置知识库的离线 RAG

首版以现有 SQLite FTS5 做检索增强生成。它能复用分块、来源校验和引用集合，生成模型只需处理相关证据。先测关键词、中文分词和术语扩展能覆盖多少任务，验收显示仍有语义漏召回时，再评估本地向量召回与关键词排序的增益。

1. **接入和索引。** 工作区显式登记库目录并按工作流启用，检索范围限于已登记来源。读取现有 `books.json`，兼容电子书原文和图版索引。新外置库首版接收带清单的 UTF-8 Markdown/TXT，登记稳定库编号、文档编号、版本、相对路径、标题、作者或机构、语言、地区、风格、来源与许可信息，以及原始文本 SHA256。图版保留页码、图号和原档链接供查阅，首版全文检索沿用已有电子文本。
2. **库版本与更新。** 原文留在选定目录，索引建在工作区管理的缓存中。默认查询只读活动索引，变更通过显式建索引生效。新索引完整验证后原子切换，失败时保留旧索引。命中片段继续核验原文，发现变更或来源不可用就提示重建或重连，其余可用库继续返回结果。历史引用保留原版本与出处，当前生成所用的集合在来源停用或改版后需要重新选择。
3. **分块和召回。** 沿标题、段落与书籍章节切分，保留原文行号和已有的页码。英文用 FTS5 词项及加权排序。中文原文建立双字词项，配合可维护的中英建筑术语表及短语加权。把明确指定的风格、地区、年代用作筛选，并区分标签对应整本书还是具体章节。检索结果按原文去重并限制单篇份额，默认展示 6 段、每文档最多 2 段，原文可单独展开。SQLite 自带的 trigram 无法直接匹配二字中文查询。[SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)
4. **进入生成。** 在现有“检索参考”里显示工作流资料和已启用书库的命中，沿用用户勾选后组成引用集合。Agent 也走同一 `retrieve` 契约。默认推荐最多 6 段、总正文 6,000 字，超出推荐值时在选集前提示，保留现有上限及旧集合行为。资料发送到生成端前复核来源和哈希，正文只传选中片段。重复参考按内容去重，发送内容不包含绝对路径、整库或完整模型。

## 二、网络搜索规则

联网改造以**模型最快拿到可用证据**为目标。计时从发出查询开始，第一条能回答问题并带有原页定位的证据到达时结束。记录冷启动与缓存命中的中位数和第 95 百分位延迟、预算内取证成功率、超时后的部分结果保留率，以及模型从取证到可引用经过的工具调用次数。先实测一次真实入口取得基线，再设延迟目标。

| 任务条件 | 路由 |
| --- | --- |
| 建模工具用法、工作区规则、已有资料可以回答的问题 | 查询本地，结果不足时展示缺口 |
| 用户说“查资料”“找参考图”，或要求核对指定网页、特定史实、当前资料 | 此次任务可联网，先确定缺少的证据，按需搜索并打开原始页面 |
| 本地证据不足且当前任务未要求联网 | 保留离线结果并指出缺口，桌面提供显式的“联网补查” |
| 用户要求纯离线 | 当次不调用搜索服务，不因未命中或断网改变模式 |

- **发什么。** 只向搜索服务发送经筛选的公开查询词，例如“哥特式 玫瑰窗 窗饰”。桌面发送前展示可编辑的查询词。工作区路径、完整任务提示词、模型坐标、项目私有名称、私有资料和 API 凭据不得进入查询正文。公开建筑的地区、年代和构件名称只在相关时加入。
- **搜什么。** 将关键疑问拆为对象与具体部位，优先原建筑管理方、遗产与博物馆机构、原图档案或研究原文。命中后记录机构、直接原页 URL、标题、访问日期和章节或图号。搜索摘要、未打开的页面、无法读取的图版只显示为线索。遇到关键来源冲突，注明各自所指对象、年代或版次及未解决之处。
- **怎样更快。** 直接给出 URL 时先打开指定页面。查询命中已知官方来源时，优先读取对应原页。需要经过搜索时，先用一条高精度查询，去重后并行读取两条候选。默认拿到首条可用证据即返回。如指定多条，则在预算内批量返回。首轮失败时可换用同义词、原文题名或备用来源。每轮至多 3 次检索、打开 6 个页面。每个来源独立计时，整轮也有截止时间。单个来源超时、限流或打不开时，返回已完成证据并指出缺口。仍在有效期的相同查询可复用已读证据。需要最新资料时重新读取原页。
- **模型怎样调用。** 设计一个研究入口接收实际要核实的问题、可选的已知链接和数量预算。同一次调用完成查询、开页、去重和证据格式整理，返回证据、尚未覆盖的问题与可重试原因。用户明确要求联网时，允许离线检索和网络取证并行启动。可从本地验证的工具和项目事实直接走本地入口。当任务只需要某一条证据时，返回该条即可，避免让模型遍历搜索结果或为同一个事实反复改写查询。
- **怎样接入。** 外部 Agent 可用共享入口，也可用宿主已有的搜索与页面读取能力，将结果按公共证据格式登记。桌面与 Agent 共用只在明确发起时运行的原页读取。广域搜索可独立配置 Brave，默认可用维基百科索引发现候选。接口返回搜索不可用、限流或页面无法打开等具体结果，保留离线候选。只有读取并匹配原页正文的结果才能加入证据。原页读取限制为公开 HTTPS，约束跳转、大小与超时，并逐跳检查实际公网地址。
- **怎样保存。** 按许可保留必要短摘录或事实提要及出处。提要标记为概述，图像保留原页链接、图注和署名。只有看过对应图版才记录其可见特征。联网结果先停留在本次参考集合，经显式收藏才进外置库索引。复查历史集合时使用当时记录的快照与哈希，需要更新时主动重查并建立新集合。

## 三、共同的证据和引用契约

沿用 `retrieve search/source/bundle/read`，候选阶段使用稳定证据编号，选集后继续用 `R1` 等任务内引用号。`retrieve architecture --library ...`、已有本地 bundle v1 和冻结工作区入口保留原调用行为。把 v2 新字段定义在共用参考协议中，由 CLI 和桌面共用校验。前端接收同一引用结构，并保留现有资产结果的类型区分。

| 内容 | 必需信息或行为 |
| --- | --- |
| 定位证据 | 来源类型、稳定编号、标题、原文位置、版本或抓取日期。书库证据绑定库清单哈希、原文 SHA256 与片段 SHA256，保留章节及行号。网络证据绑定原页 URL、访问日期、机构、页面位置与所存内容的 SHA256 |
| 可追溯程度 | 本地资料由引擎回源校验。桌面服务成功读取原页后标记已读取。宿主 Agent 导入的记录标明由谁读取，桌面不把导入声明显示成自己查证。只有摘要、链接或访问失败的候选不进入生成用证据集合 |
| 下发和复查 | 生成端继续只接受 `bundle id + sha256` 校验过的集合。旧编号只能在原集合内解释。任务日志记录编号、链接或位置和哈希，引用正文通过参考集合读取。历史证据供应与当前是否启用分别显示 |
| 落到建筑 | 记录来源支持的事实、设计采用的方块表达和实际检查结果。界面把“已提供”与“已引用”分别显示。检查生成端返回的引用编号是否属于本次集合。模型几何、净空和实际渲染仍通过对应工具验证 |

## 实施顺序与验收

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| 1. 外置库离线接入 | 扩展 Python `nbt_architecture_knowledge.py`、`nbt_text_search.py` 与 `nbt_retrieval.py`，接上现有候选、选集、复查流程。增加库登记、显式建索引及状态。同步参考说明和 Agent 路由 | 原 10 项测试继续通过。覆盖改版、篡改、停用、复制或移动工作区、旧集合和多库部分失败。建立 30 个带人工标注的可答查询，覆盖中文、英文、跨语言、同名异义，验收目标为至少 24 个查询在前 5 条有一条正确证据，同时保留无关查询用例 |
| 2. 统一联网取证 | 定义单次研究入口和证据登记接口，适配宿主 Agent。桌面在现有 `reference-picker.js` 增加显式联网选项和证据状态，沿用 `internal-ai.cjs` 的引用读取路径 | 模拟服务验证命中后提前结束、一处失败仍返回其余结果、离线流程零联网、请求发送范围。用一个真实搜索入口核对原页与定位，并报告首条可用证据延迟及预算内成功率 |
| 3. 用建筑成品检验 | 用哥特教堂的飞扶壁与玫瑰窗、另一种构造体系的原创建筑复跑。端到端走查询、选集、设计、保存初稿和真实预览 | 每处采纳的资料能回查到原文。记录首次用对入口、额外查询次数、最终提供的片段数和正文长度。两次创作都验证实际方块表达，和仅把来源链接写进报告区分开来 |

验证沿用现有引擎检索、桌面参考选择器与 Node 模拟生成测试。开发从 NBTCreator 源码根目录运行 `mise exec -- python -B tests/engine/architecture-knowledge.py`、`mise exec -- python -B tests/engine/retrieval.py` 和 `mise exec -- node --test tests/node/retrieval.test.cjs`。桌面测试先执行 `mise run ci:build`，再执行 `mise exec -- node tests/desktop/retrieval-desktop.mjs`。涉及工具目录或命令描述时同时执行 `npm run sync:tools` 与 `npm run check:tools`，均通过 mise 运行。

第一阶段在现有 15 本书、9,108 段原文上验证，30 个标注查询均在前 5 条命中，无关查询返回空结果。在本机的检索函数测得中位数约 21 毫秒、第 95 百分位约 36 毫秒，计时包含选定库检索和原文校验。可从源码根目录用 `mise exec -- python -B tests/engine/architecture-retrieval-benchmark.py --library <现有书库目录>` 复跑，索引写入独立临时工作区。

第二阶段用「圣礼拜堂 玫瑰窗 重建年代」测试实际原页。5 次重新取证均取得包含 1485 年的原文，首条证据耗时中位数 402 毫秒，最慢 633 毫秒。另做 3 次缓存复查，查证中位数 0.9 毫秒。完整 CLI 从进程启动到返回仍需约 0.8～1.4 秒。这是一条已知官方来源的实测，维基百科索引在当前环境连接超时，Brave 广域搜索尚无实际服务测试数据。桌面模拟验证了联网查询要显式发起、本地选段仍可一同引用，生成及已选快照复查无需重新读取网页。

网页摘录可经显式收藏加入各工作流的离线索引。收藏保留快照出处，取消后历史集合仍可复核。用玫瑰窗石骨和垫席隔扇两个构造样件复跑了离线检索、选集、候选预览、SNBT 制作版保存和纹理出图。玫瑰窗使用一条网站收藏和一段书库证据，隔扇使用一段日式住宅资料。实测落实了石环与窗饰、垫席分格与隔扇开口，验证范围是两个构造样件。

## 用珍珠光教堂复查规则

本地先查「飞扶壁 尖拱」获取构造背景。用户明确要参考资料时，再联网核对玫瑰窗的时代与图像。法国国家古迹中心把圣礼拜堂最初的西立面玫瑰窗和约 1485 年改建的现存启示录玫瑰窗区分开来。对应方块设计可以使用八分窗饰和石环做原创表达，设计记录标明这是体素适配。最后用正立面近景核对窗饰、内部近景核对透空效果，建筑通路仍以模型实测为准。[放射式哥特](https://www.sainte-chapelle.fr/en/discover/the-radiant-gothic) · [启示录玫瑰窗](https://www.sainte-chapelle.fr/en/discover/the-rose-of-the-apocalypse)
